# brover_simulation

ROS 2 Jazzy пакет с упрощенной моделью ровера BRover-E5 для Gazebo Sim и RViz.

Модель предназначена для быстрого запуска симуляции, проверки управления через ROS 2 и получения базовых данных с виртуальных сенсоров. Внешний вид упрощен: корпус сделан прямоугольником, а колеса, подвеска, дифференциал и передняя камера основаны на облегченных mesh-файлах.

## Возможности

- запуск BRover-E5 в Gazebo Sim;
- просмотр модели в RViz без запуска Gazebo;
- управление через `/cmd_vel`;
- управление ровером с клавиатуры;
- публикация одометрии в `/odom`;
- публикация двумерной позы ровера в `/odom_pose2d`;
- TF и симуляционное время `/clock`;
- виртуальная IMU с топиком `/bhi360/imu`;
- виртуальный лидар с топиком `/scan`;
- виртуальная передняя камера с raw/JPEG изображением и CameraInfo;
- шестиколесная skid-steer схема на базе Gazebo Sim `DiffDrive`.

## Требования

- Ubuntu 24.04;
- ROS 2 Jazzy Jalisco;
- Gazebo Sim из пакетов `ros-jazzy-ros-gz`;
- `colcon`.

## Полная инструкция по установке и запуску

Подробная инструкция по подготовке Ubuntu 24.04, установке зависимостей, сборке пакета и запуску симуляции находится в файлах:

- `Инструкция по запуску brover_simulation.docx` - версия для Microsoft Word;
- `Инструкция по запуску brover_simulation.odt` - версия в формате OpenDocument для Ubuntu/LibreOffice.

В инструкции приведены разделы по установке ROS 2 Jazzy, настройке рабочего окружения, установке Gazebo Harmonic, установке пакета `brover_simulation` и запуску симуляции ровера.

## Сборка

```bash
git clone https://github.com/NikolayIvanovWS/brover_simulation.git
cd brover_simulation

colcon build
```

## Просмотр модели в RViz

RViz можно запустить без Gazebo. Этот режим удобен, чтобы быстро проверить внешний вид URDF-модели, TF-дерево и расположение визуальных элементов.

```bash
ros2 launch brover_simulation rviz.launch.py
```

Launch-файл запускает:

- `joint_state_publisher`;
- `robot_state_publisher`;
- `rviz2` с готовой конфигурацией `brover_e5.rviz`.

В этом режиме топики Gazebo-сенсоров (`/scan`, `/camera1/image_raw`, `/odom`) **не публикуются**, потому что сама симуляция не запущена. Для проверки сенсоров используйте запуск Gazebo.

Если RViz используется одновременно с запущенной симуляцией Gazebo для просмотра `/scan`, `/odom` или камеры, запускайте его с симуляционным временем:

```bash
ros2 launch brover_simulation rviz.launch.py use_sim_time:=true
```

## Запуск симуляции

```bash
ros2 launch brover_simulation gazebo.launch.py
```

По умолчанию запускается пустой мир `empty`. Можно выбрать другой мир через аргумент `world`:

```bash
ros2 launch brover_simulation gazebo.launch.py world:=test_yard
ros2 launch brover_simulation gazebo.launch.py world:=rough_terrain
ros2 launch brover_simulation gazebo.launch.py world:=indoor_corridor
ros2 launch brover_simulation gazebo.launch.py world:=sensor_test_world
ros2 launch brover_simulation gazebo.launch.py world:=obstacle_course
ros2 launch brover_simulation gazebo.launch.py world:=calibration_world
ros2 launch brover_simulation gazebo.launch.py world:=left_wall
```

Доступные миры:

- `empty` - базовая плоскость для быстрой проверки модели и топиков;
- `test_yard` - тестовый полигон со стенами и препятствиями для проверки лидара и камеры;
- `rough_terrain` - простой неровный участок с рампами, ступенью и камнями для проверки движения;
- `indoor_corridor` - коридорная среда со стенами и поворотами для проверки лидара в ограниченном пространстве;
- `sensor_test_world` - стенд с панелями и объектами на известных расстояниях для проверки `/scan` и камеры;
- `obstacle_course` - полоса препятствий со стойками, воротами, ступенью и рампой для ручного управления;
- `calibration_world` - калибровочный мир с метровой линейкой по оси X и угловыми лучами 45, 90, 135, 180, -45, -90 и -135 градусов. Зеленая ось показывает движение вперед, оранжевая - назад, синие лучи - положительные углы, красные - отрицательные;
- `left_wall` - мир с длинной стеной слева от ровера: длина 10 м, высота 1 м, центр стены на расстоянии 1.5 м по оси `+Y`.

## Управление ровером

### Управление с клавиатуры

В отдельном терминале:

```bash
ros2 run brover_simulation keyboard_teleop.py
```

Клавиши управления работают в режиме удержания: ровер движется только пока соответствующая клавиша нажата. Если клавиша не нажата, публикуется нулевая скорость.

Клавиши управления:

- удерживать `w` - движение вперед;
- удерживать `s` - движение назад;
- удерживать `a` - поворот влево;
- удерживать `d` - поворот вправо;
- `x` или `Space` - остановка;
- `q` / `z` - увеличить / уменьшить линейную скорость;
- `e` / `c` - увеличить / уменьшить угловую скорость.

Терминал с `keyboard_teleop.py` должен быть активным, чтобы нажатия клавиш попадали в node.

## Проверка топиков

Список топиков:

```bash
ros2 topic list
```

Одометрия:

```bash
ros2 topic echo /odom
```

Двумерная поза ровера:

```bash
ros2 topic echo /odom_pose2d
```

Топик `/odom_pose2d` имеет тип `geometry_msgs/msg/Pose2D`: `x` и `y` задают положение ровера на плоскости, `theta` задает угол поворота вокруг вертикальной оси в радианах, нормализованный в диапазоне [-pi, pi].

Лидар:

```bash
ros2 topic echo /scan
```

В текущей настройке лидара `ranges[0]` направлен вперед по ходу ровера.

Камера:

```bash
ros2 topic hz /camera1/image_raw
ros2 topic echo /camera1/camera_info --once
```

Топики `/scan`, `/camera1/image_raw` и `/camera1/camera_info` публикуются вспомогательным node `sensor_topic_normalizer.py`. Он получает внутренние данные сенсоров из Gazebo, задает корректные `frame_id` и оставляет пользовательские имена топиков стабильными.

## Состав пакета

Репозиторий является ROS 2 пакетом `brover_simulation`: `package.xml` и `CMakeLists.txt` находятся в корне проекта.

- `package.xml` - описание ROS 2 пакета и зависимостей;
- `CMakeLists.txt` - правила установки launch-файлов, URDF, миров, mesh-файлов и вспомогательных скриптов;
- `urdf/brover_e5.urdf.xacro` - описание модели;
- `launch/gazebo.launch.py` - запуск Gazebo Sim, спавн модели и bridge;
- `launch/rviz.launch.py` - просмотр модели в RViz;
- `rviz/brover_e5.rviz` - конфигурация RViz;
- `config/bridge.yaml` - мост Gazebo <-> ROS 2;
- `scripts/` - вспомогательные ROS 2 node-скрипты для `/odom_pose2d`, сенсорных топиков и управления с клавиатуры;
- `worlds/` - миры Gazebo для разных сценариев;
- `meshes/` - облегченные mesh-файлы колес, подвески, дифференциала и камеры.

## Сброс одометрии

Сервис /odom/reset имеет тип std_srvs/srv/Empty. Он обнуляет локальные
координаты x/y и угол, сохраняя положение модели в мире Gazebo.
Вызывайте его после остановки ровера:

    ros2 service call /odom/reset std_srvs/srv/Empty '{}'

После сброса положительное направление локальной оси X совпадает
с направлением ровера в момент сброса. /odom, /odom_pose2d и преобразование
odom → base_footprint используют общее начало координат.
Сервис доступен после получения первого сообщения одометрии.

На паузе сброс использует последние полученные данные. Новое преобразование
TF с обновленным временем поступает после возобновления симуляции.
При сбросе времени симуляции прежнее смещение одометрии отбрасывается.

## Единицы угла

/odom_pose2d.theta задается в радианах: 90° соответствует pi/2, 180° — pi.
В прежних версиях этот топик использовал градусы. При обновлении учебных
программ проверьте единицы сравнений угла. Для вывода градусов используйте
math.degrees(theta).

## Ограничения управления

Команды geometry_msgs/msg/Twist поступают в /cmd_vel: linear.x — м/с,
angular.z — рад/с. Перед приводом они проходят ограничение скорости.
Параметры задаются при запуске узла в config/control.yaml:

| Параметр | Значение по умолчанию |
| --- | --- |
| Максимальная линейная скорость | 0.375 м/с |
| Максимальная скорость борта | 6 рад/с при расчетном радиусе 0.0625 м |
| Минимальная ненулевая скорость борта | 1 рад/с |
| Мертвая зона | меньше 0.2 рад/с |
| Расчетная колея контроллера | 0.42 м |
| Период передачи команды | 0.05 с реального времени |
| Тайм-аут входной команды | 0.25 с реального времени |

При насыщении скорости бортов масштабируются вместе. Затем применяются
мертвая зона и минимальная скорость. Поэтому небольшая ненулевая команда
может дать ноль или скорость выше запрошенной. Для прямого движения
команда меньше 0.0125 м/с дает ноль, а команда 0.02 м/с дает 0.0625 м/с.
Вращение на месте ограничено примерно 1.786 рад/с.
Нулевая команда всегда останавливает, NaN/Inf также дают остановку.

Команды нужно передавать непрерывно с интервалом меньше тайм-аута.
После прекращения /cmd_vel узел передает ноль не позднее следующего периода
после тайм-аута; физическое торможение зависит от ускорений привода Gazebo.
Тайм-аут действует и при паузе. После паузы дольше тайм-аута требуется свежая
команда; обратный скачок времени также отменяет прежнюю команду.
До получения /clock движение не разрешается.

При завершении узла command_limiter launch завершает всю симуляцию.
Это не отдельный watchdog внутри Gazebo: остановка при аварии узла обеспечена
завершением симуляции. Не отправляйте команды во внутренний топик
/_brover_simulation/cmd_vel — он предназначен для связи узла с мостом.

Расчетные радиус и колея контроллера задают ограничения команд и не заменяют
геометрию или калибровочные параметры физической модели.

## Виртуальная IMU

Топик /bhi360/imu имеет тип sensor_msgs/msg/Imu и frame_id imu_link.
Оси сенсора: X вперед, Y влево, Z вверх. Сенсор расположен на 0.035 м выше
начала base_link. Это условное размещение виртуального сенсора.
IMU публикует quaternion ориентации, угловую скорость в рад/с и ускорение
в м/с². Данные не объединяются с одометрией.

Частота по умолчанию — 100 Гц времени симуляции. Ее можно изменить:

    ros2 launch brover_simulation gazebo.launch.py world:=calibration_world imu_rate:=500.0

Параметр imu_rate должен быть положительным. Частота получения по реальному
времени зависит от скорости симуляции и нагрузки.
Виртуальный сенсор не моделирует шум и калибровку конкретной аппаратной IMU;
нулевые covariance означают, что оценка неопределенности не задана.
Сервис /odom/reset меняет локальную одометрию, а не ориентацию IMU.

Проверка данных:

    ros2 topic echo /bhi360/imu --once --no-daemon

## Интерфейсы камеры

| Топик | Тип | Назначение |
| --- | --- | --- |
| /camera1/image_raw | sensor_msgs/msg/Image | Изображение RGB |
| /camera1/camera_info | sensor_msgs/msg/CameraInfo | Параметры виртуальной камеры |
| /image_raw/compressed | sensor_msgs/msg/CompressedImage | JPEG |

У raw, JPEG и CameraInfo одного кадра одинаковые stamp и frame_id.
Система координат front_camera_optical_frame: X вправо, Y вниз, Z вперед.
Она связана фиксированным TF с front_camera_link; положение физической камеры
в модели не изменилось.

По умолчанию: 640×480, 30 Гц времени симуляции, горизонтальный FOV 1.047 рад,
JPEG quality 85. CameraInfo рассчитывается по фактическому размеру и тому же FOV.
JPEG с потерями: пиксели после декодирования могут отличаться от raw.

Параметры запуска:

    ros2 launch brover_simulation gazebo.launch.py world:=sensor_test_world camera_rate:=15.0 jpeg_quality:=80

Для уменьшения нагрузки:

    ros2 launch brover_simulation gazebo.launch.py world:=sensor_test_world camera_width:=320 camera_height:=240 camera_rate:=10.0

Доступны camera_width, camera_height, camera_rate, camera_horizontal_fov,
jpeg_quality. Размер и частота должны быть положительными, FOV — между 0 и pi,
JPEG quality — целое от 1 до 100. Частота приема по реальному времени зависит
от скорости симуляции и нагрузки.

Для JPEG используются cv_bridge и OpenCV. Зависимости рабочего пространства
можно установить через rosdep из корня рабочего пространства:

    rosdep install --from-paths src --ignore-src -r -y
